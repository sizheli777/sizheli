## 一、选题与需求分析

### 1.1 选题背景

在日常工作和学习中，数据分析是一项高频需求。然而，传统数据分析需要用户掌握 Python/R、pandas、matplotlib 等编程技能，这对非技术用户构成了较高的门槛。大语言模型（LLM）的出现使得"自然语言 → 代码"的转换成为可能。

### 1.2 解决什么问题

本项目开发的 **AI 数据分析助手** 解决了以下痛点：

1. **编程门槛高：** 用户无需编写代码，通过自然语言即可完成数据分析
2. **工具切换繁琐：** 将数据查询、统计、可视化集成在一个对话式界面中
3. **学习成本：** 用户可以直接看到 AI 生成的分析代码，边用边学

### 1.3 AI 角色定义

LLM 在本系统中扮演 **数据分析师** 的角色：
- 理解用户的数据分析需求
- 根据数据 Schema 设计分析方案
- 生成 pandas/matplotlib 代码
- 用中文解释分析结果

### 1.4 目标用户

- 不懂编程但需要分析数据的业务人员
- 需要快速探索数据的学生和研究人员
- 希望通过自然语言交互学习数据分析的入门者

### 2.2 技术选型理由

| 技术 | 版本 | 选型理由 |
|------|------|----------|
| **Streamlit** | ≥1.28 | 专为数据应用设计的 Python Web 框架，原生支持图表、DataFrame 展示，开发效率极高 |
| **pandas** | ≥2.0 | 数据分析领域的事实标准，LLM 训练数据中大量覆盖 |
| **matplotlib + seaborn** | ≥3.7 / ≥0.12 | LLM 最熟悉的可视化库，生成的代码正确率最高 |
| **openai SDK** | ≥1.0 | OpenAI 兼容接口，同时支持 DeepSeek、OpenAI 等多种后端 |
| **DeepSeek API** | - | 性价比极高（百万 token 仅需 2 元），中文能力强，OpenAI 兼容 |
| **scipy** | ≥1.10 | 统计分析支撑库 |

### 2.3 为什么不用其他方案

- **Gradio vs Streamlit：** Gradio 更适合 ML 模型演示，Streamlit 对数据表格和图表的原生支持更好
- **Plotly vs matplotlib：** Plotly 交互性好但 LLM 生成的 Plotly 代码错误率较高；matplotlib 是 LLM 训练数据中占比最大的可视化库，生成准确率更高
- **LangChain vs 原生 SDK：** LangChain 抽象层太厚，调试困难；直接使用 openai SDK 更可控

## 三、关键实现说明

### 3.1 数据加载模块 (`data_loader.py`)

**核心功能：**
- 自动识别 CSV 和 Excel (.xlsx/.xls) 文件格式
- CSV 多编码兼容：依次尝试 UTF-8 → GBK → GB2312 → Latin-1
- 自动生成数据 Schema 描述，供 LLM Prompt 使用

**关键实现：**
```python
# 多编码自动检测
for encoding in ["utf-8", "gbk", "gb2312", "latin-1"]:
    try:
        return pd.read_csv(io.BytesIO(file_content), encoding=encoding)
    except (UnicodeDecodeError, UnicodeError):
        continue
```

`get_data_schema_for_prompt()` 函数将 DataFrame 结构化为 LLM 可理解的文本描述，包含列名、数据类型、缺失值统计和样本数据。

### 3.2 LLM 服务模块 (`llm_service.py`)

**核心策略：System Prompt 工程**

系统提示词的设计是本项目的核心。经过多轮迭代优化：

1. **角色设定：** "你是一个专业的数据分析助手"
2. **数据注入：** 将数据 Schema 动态插入 System Prompt
3. **约束规则：** 明确可用库、变量名 `df`、不需要 `plt.show()`、中文支持设置
4. **输出格式：** 严格要求 JSON 格式（含 explanation / code / answer 三个字段）

**JSON 解析的鲁棒性处理：**

LLM 输出格式不稳定是常见问题。本模块实现了多层降级解析策略：

```python
# 1) 直接 json.loads()
# 2) 提取 ```json ... ``` 代码块
# 3) 提取 ``` ... ``` 无语言标识代码块
# 4) 正则匹配第一个 {...} 对象
# 5) 降级返回（将原始内容作为 answer）
```

### 3.3 代码执行模块 (`code_executor.py`)

这是最具技术挑战的模块，需要平衡安全性和功能性。

**安全措施：**

| 措施 | 实现方式 |
|------|----------|
| 模块白名单 | 只允许 pandas, numpy, matplotlib, seaborn, scipy.stats |
| 内置函数限制 | 重写 `__builtins__`，禁用 `__import__`、`eval`、`exec`、`open`、`os` 等 |
| 执行超时 | `threading.Timer` 实现 30 秒超时中断 |
| 输出沙箱 | 捕获 stdout，隔离打印输出 |
| 数据副本 | 对原始 DataFrame 做 `.copy()` 防止意外修改 |

**图表捕获机制：**

```python
# 执行前清除旧图表
plt.close("all")
# 执行代码...
# 执行后收集所有图表
figures = [plt.figure(n) for n in plt.get_fignums()]
```

所有图表设置为非交互式后端 `matplotlib.use("Agg")`，确保在无 GUI 环境中正常运行。

### 3.4 主应用 (`app.py`)

**UI 设计：**

- **3 Tab 布局：** 数据概览 → 智能分析 → 分析历史
- **侧边栏：** API 配置 + 文件上传 + 会话管理
- **聊天式交互：** 使用 `st.chat_message` 和 `st.chat_input` 构建对话界面
- **演示数据：** 内置销售数据样例，方便零门槛体验

**状态管理：**

使用 `st.session_state` 管理全局状态：
- `df`: 当前数据框
- `messages`: 对话历史
- `client`: OpenAI 客户端实例
- `system_prompt`: 动态生成的系统提示

### 4.3 局限性分析

1. **LLM 生成代码的不确定性**
   - 同一问题可能生成不同代码，偶尔出现语法错误或逻辑错误
   - 复杂分析（如多表连接、时间序列预测）可能生成不完整的代码
   - **改进方向：** 增加代码预检步骤，尝试自动修复常见错误

2. **代码执行安全性**
   - `exec()` 本质上是危险的，白名单机制不能 100% 保证安全
   - 不适合在不可信的多用户环境中部署
   - **改进方向：** 使用 Docker 沙箱或 WebAssembly (Pyodide) 隔离执行

3. **图表中文显示**
   - 依赖系统安装中文字体（SimHei），某些环境可能显示方块
   - **改进方向：** 自动下载中文字体或使用英文标签

4. **大文件处理**
   - 大 CSV（>10 万行）会导致 Prompt 过长，超出 LLM 上下文窗口
   - **改进方向：** 智能采样 + 数据 Schema 压缩

5. **对话上下文**
   - 当前保留最近 3 轮对话，复杂的多步分析可能丢失上下文
   - **改进方向：** 实现更智能的上下文摘要

## 五、个人收获与改进方向

### 5.1 个人收获

1. **LLM 应用开发全流程：** 从需求分析 → Prompt 工程 → API 集成 → 结果处理 → UI 构建
2. **Prompt Engineering 实践：** 深入理解了 System Prompt 的设计方法、JSON 输出约束、鲁棒性解析
3. **安全 vs 功能平衡：** 在代码沙箱设计中体会到安全性和功能性的权衡
4. **Streamlit 框架：** 掌握了快速构建数据应用的方法
5. **工程化思维：** 模块化设计、错误处理、状态管理的综合运用

### 5.2 改进方向

1. **多数据源支持：** 支持数据库连接（MySQL/PostgreSQL）、API 数据源
2. **自动报告生成：** 一键生成完整的数据分析报告（PDF/HTML）
3. **多轮深度分析：** 增强上下文管理，支持多轮递进式分析
4. **Agent 模式：** 让 LLM 自主规划分析路径，多步迭代
5. **代码缓存：** 缓存已验证正确的分析代码，避免重复调用 LLM
6. **结果对比：** 支持多次分析结果的并排对比
